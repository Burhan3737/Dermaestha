## Summary
Interactive root-cause debugging of a "broken booking/payment flow." First attempt (Bug #1) built a "Resume payment" recovery affordance for the ACTIVE_LOCK_EXISTS dead-end. On further testing the REAL root cause surfaced: `.env` set no provider vars, so `PAYMENT_PROVIDER`/`VIDEO_PROVIDER`/`EMAIL_PROVIDER` all defaulted to `stub`, and the payment stub throws 501 on every `/pay` — payment could never start, which is what made the flow look "stuck." Fixed by setting the dev mock providers in `.env`. With real (mock) payments working, the lock dead-end shrank to a minor self-healing edge case, so the user chose to **fully revert** the Bug-#1 code and defer any active-lock UX. Net code change: none.

## Context / why
User hit "Finish your current booking first." then a "stuck at resume/confirm" loop. The visible symptoms (409 ACTIVE_LOCK_EXISTS, 429 rate-limit) were shallow masks; peeling them off (disable rate limit → reproduce) revealed `POST /pay` returning 501 because the payment provider was the throwing stub. The original Bug-#1 "Resume affordance" was premised on the pre-fix world where every payment failed and every attempt left an orphaned lock.

## Dependencies / config / schema
- LOCAL ENV FIX (`.env`, gitignored — not committed; THE actual fix): added `PAYMENT_PROVIDER=mock`, `VIDEO_PROVIDER=mock`, `EMAIL_PROVIDER=console`. Root cause: all three were unset → defaulted to `stub` (`env.js:17/18/24`); `payfast.stub.createCheckout` throws `AppError('NOT_IMPLEMENTED', …, 501)` → every `POST /pay` 501'd → flow dead-ended. Mock providers run the same prod logic (signed IPN → verifyWebhook → processWebhook) via the dev `/dev/checkout` + `/dev/video/*` simulators. Verified: `GET /dev/checkout` → 200 (route mounts only when PAYMENT_PROVIDER=mock); a booking reached `confirmed` via mock Pay.
- SESSION-ONLY DEBUG (no code change, auto-reverts on normal restart): :3000 launched with env override `PAYMENT_INTENT_MAX_PER_PATIENT_HOUR=100000000` to disable the per-patient `/pay` rate limit while reproducing. The limiter is NOT a bug — correctly keyed per-patient (`appointment/index.js:14`). The 429 was a testing artifact masking the 501.

## Decisions
- **Reverted Bug #1 entirely** (user-directed). Rationale: the lock dead-end's severity was inflated by the 501 misconfig (every payment failed → constant orphaned locks). Once mock payments work, an abandoned checkout leaves a lock that self-heals in ≤10 min — a minor edge case not worth a server change + re-pay button (which itself can loop the user back into an abandonable checkout).
- Fixed the real root cause as local config (`.env` mock providers), not code.
- Active-lock UX (was deferred, then chosen): make the live hold **discoverable in the patient Upcoming list** with a "Complete payment" action — rather than a booking-error interstitial (the reverted Bug-#1, which looped). Widening the existing `active` list is minimal and self-cleaning (expired holds drop via the `lockExpiresAt > now` filter; paid → `confirmed` renders normally).

## Notable findings
- Provider selection (`integrations/payment/index.js`) falls back to a 501-throwing stub when `PAYMENT_PROVIDER` is unset; the same pattern applies to video/email. Local `.env` shipped without these set.
- The mock payment design is a faithful repro: the dev checkout page builds a real HMAC-signed IPN and runs it through the production webhook path (not a shortcut).
- Single-Lock guard is correct; `slot_locked` holds are invisible in the patient Upcoming view (only confirmed/in_progress) — noted, not changed.
- No worker expires `slot_locked` rows; expiry is lazy (ADR-23) — a live lock blocks rebooking for the full 10-min TTL.
