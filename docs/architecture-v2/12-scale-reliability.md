# 12 — Scale & Reliability

---

## Load at Launch

| Metric | Value | Implication |
|---|---|---|
| Active doctors | ~10 | Single-digit concurrency |
| Bookings/week | ~100 | ~14/day, ~2/hour peak — trivial for a single Postgres instance |
| Video sessions | ~100/week | Handled entirely by Daily.co CDN; zero Express CPU/memory load |
| PDF writes | ~100/week | ~50KB each → ~5MB/week Railway volume usage |
| Reminder emails | ~300/week | Booking confirm + 2 reminders per appointment |
| DB queries/minute | <10 | No connection pooler or cache needed |

**Conclusion:** The entire v1 workload fits on Railway's smallest tier. Single process, single DB instance, no clustering.

---

## Failure Modes & Mitigations

| Component | Failure scenario | v1 mitigation |
|---|---|---|
| Daily.co room creation | API timeout or rate limit during booking | `try/catch` → 503 to client; patient retries; appointment not written to DB |
| Resend email delivery | Delivery failure post-booking | Log + continue; booking is already written to DB; patient can see appointment in dashboard |
| PDFKit render | Crash mid-render | `try/catch`; Prescription record is persisted; PDF can be re-generated by re-triggering the route |
| node-cron | Server restart during a 5-minute tick window | ±5 min query window + `notified` boolean: appointment will be caught on the next tick; no duplicates |
| Railway volume | Disk space exhaustion | 1000 prescriptions ≈ 50MB; monitor Railway dashboard; trivial to clean at this scale |
| Double-booking | Two patients submit for the same slot simultaneously | `findFirst` check before `create` — first write wins, second gets 409 |
| JWT compromise | Stolen token used before expiry | 7-day expiry limits window; add Redis denylist in v1.1 if instant revocation is required |
| Postgres connection | Connection count limit hit | At <10 concurrent users, Prisma's default pool is sufficient; add PgBouncer if errors appear |

## Scaling Path (Post-Launch)

These are additions, not rewrites. The v1 architecture was chosen to allow each as a one- or two-file change.

| Step | Trigger | Action | Code changes |
|---|---|---|---|
| 1 | Connection errors under load | Add PgBouncer | Railway plugin — zero code changes |
| 2 | Express CPU bottleneck | Horizontal scaling | Add Railway replica — zero code changes |
| 3 | Railway volume approaching limit | Migrate PDFs to S3 | Change `services/pdf.js` write target + `GET /prescriptions/:id/pdf` redirect. Two files. |
| 4 | Email failure rate > 1% | Add retry logic + queue | Wrap `services/email.js` calls in BullMQ — adds Redis dependency |
| 5 | DB read latency > 200ms | Read replica | Prisma `$extends` for read/write splitting — no route changes |
| 6 | Cron reliability issues | Extract worker | Move `services/scheduler.js` to a separate Railway worker service |

None of these require architectural redesign.
